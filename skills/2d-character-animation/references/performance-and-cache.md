# 性能、预加载与缓存

## 先量而不是先削减效果

固定角色数、并行数、DPR、浏览器、运行时版本、视口与采样时长；性能采样单独运行，不同时构建或运行其他浏览器大套测试。区分网络、解码、主线程、layout/paint 与 GPU 合成瓶颈。

记录帧间隔 p50/p95/p99、最大值、超过 50ms 的帧数、输入响应、骨骼更新数和截图/录屏。RAF 频率本身不证明画面每帧更新：同时验证可见骨矩阵变化及真实录屏。

60Hz 的理想帧预算约 16.7ms，120Hz 约 8.3ms；先记录设备刷新率。案例曾用 p95 < 50ms、max < 250ms 作为“严重卡顿回归”门槛，这远低于稳定 60fps 的要求，不能称为行业流畅标准。预算由目标设备和对照基线确定。

## 按成本排序修复

1. **静态美术成本**：反复在每个骨骼上画完整 atlas、叠滤镜染色，会把小人物变成很多大纹理采样。离线遮罩染色、裁切，再输出足够分辨率的 WebP/PNG 小附件；保留源 PNG 与标定供再生成。
2. **解码/重复资源**：中性头、腿、道具可被不同服色共享；静态裁切贴图按内容 hash 命名。不要每次动作切换重新编码 SVG data URL 或重建 image。
3. **React 重渲染**：memoize 静态 rig，ref/渲染实体驱动连续姿态；进度条自己订阅进度，不让每下载一张图都重渲染满场人物。
4. **DOM 写入**：缓存上一帧 transform，只提交变化的骨骼；idle 只动必要关节，静止角色不创建常驻时间轴。避免每帧为全部关节设置相同属性。
5. **布局**：先批量读取全场几何，再做写入；仅在场景/尺寸变化时重测。root 优先 transform，避免反复改 top/left。SVG transform、滤镜与巨大纹理仍可能重绘，不能承诺“用了 transform 就全走 GPU”。
6. **合成层与并行**：不要给每根骨头都加 will-change/force3D；按真实成本选择 Canvas/WebGL、sprite atlas 或保留 SVG。引擎迁移需要瓶颈证据，不是第一步。

## 分清五种“缓存”

| 层 | 解决什么 | 不能保证 |
| --- | --- | --- |
| HTTP cache | 普通重复请求 | 永久离线保留 |
| CacheStorage | 跨刷新保留明确资源 | 永不被系统清理 |
| 内存 Blob/ObjectURL | 同会话复用数据来源 | 图片已经完成解码 |
| decoded image | 避免首次绘制才解码 | 永久保留或已上传 GPU |
| GPU 纹理 | 当前渲染使用 | 由 JS 缓存直接保证驻留 |

预加载适合资源集小、下一阶段明确、首帧缺图影响大的房间等待期。先关键角色与共用片，再有预算地加载其余变体；并发和解码内存要限额，不能一次加载所有游戏的全部资源。

room-owned session 放在回合/阶段 key 之上，跨开局复用；离开释放消费者持有的对象 URL 和解码引用，但按缓存策略保留磁盘缓存。暂停时 abort 未完成工作，重新进入补齐；去重还在进行的相同请求。版本更新需淘汰不可达旧项，不能无限追加。

缓存拒绝、空间不足或不支持 API 时应退回正常资源路径。失败不计入完成；恢复重试不重播动画。在需要完整身体首帧的场景，附件全部 ready 后再显露角色绘图层，不能先露一堆连接圆点；保留布局、用户身份和可操作控件。不要因此把整个房间隐藏。

进度含义先说明：按文件、字节还是资源可绘制程度。本案例使用 ready/total 的文件比例，下载失败或待解码项不计 ready，完成后常驻 100%。不要把无可靠 Content-Length 的下载伪装成精确字节进度；隐藏还是保留进度由当前产品约定。

## 验证缓存真的有用

冷缓存记录请求数、传输量和可绘制时间；同会话进入满场不得重复请求；刷新后验证持久缓存命中；缓存拒绝、清除、离开、断线、低内存与新版本分别测试。解码内存估算可从宽×高×4 开始，另外留浏览器/纹理复制余量，不能只看压缩文件体积。

浏览器模拟、CPU throttling 和桌面 WebKit 是必要证据，但不等同于实体 iPhone 的温控、Safari、静音开关和系统缓存驱逐表现。音频用项目已有共享 session，在 ready/start 手势中解锁；iOS 的 Audio Session 行为须用实体设备验证。
